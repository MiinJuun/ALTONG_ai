# 협업 규칙

## 브랜치와 병합

- `main`: 발표·제출 가능한 안정 버전. 직접 push하지 않는다.
- `develop`: 기능 통합 브랜치. 간단한 수정과 문서 변경은 직접 push할 수 있다.
- 큰 기능이나 다른 모듈에 영향을 주는 작업은 `develop`에서 작업 브랜치를 만들고 PR로 `develop`에 병합한다.
- 안정된 버전은 `develop`에서 `main`으로 PR을 만들어 반영한다.
- 병합 방식은 **Create a merge commit**이다. 병합된 작업 브랜치는 삭제하며 `main`과 `develop`은 유지한다.

작업 브랜치는 `<type>/<main-topic>`으로 이름 짓는다. 영문 소문자와 하이픈을 사용하고 작업 번호·담당자 이름은 넣지 않는다.

- type: `feature`, `fix`, `docs`, `refactor`, `test`, `chore`
- 예: `feature/focus-timer`, `fix/tray-exit`, `docs/readme`

## 커밋과 PR

커밋 제목은 영어로 `<type>: <subject>` 형식을 사용한다. type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`다.

```text
feat: add focus session timer
fix: prevent duplicate tray icons
```

PR 제목은 `<type>: <한국어 제목>` 형식으로 작성한다. type은 커밋과 동일하게 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`를 사용한다.

```text
feat: 집중 모드 타이머 추가
fix: 트레이 아이콘 중복 생성 문제 수정
docs: 협업 규칙 문서 추가
```

PR 본문은 한국어로 자유롭게 작성한다. 변경 내용, 확인 결과, 다른 모듈에 미치는 영향을 짧게 적는다. 공통 데이터 형태나 다른 모듈의 사용법을 변경할 때는 관련 팀원과 먼저 확인한다.

GitHub Issues, Issue Template, PR Template은 사용하지 않는다.

## Python 개발 환경

- 프로젝트에서 합의한 Python 버전을 사용한다.
- 프로젝트별 가상환경을 사용하며 `.venv` 폴더는 커밋하지 않는다.
- 새로운 라이브러리를 설치하거나 버전을 변경하면 프로젝트에서 사용하는 의존성 파일도 함께 갱신한다.
- 실행·설치·테스트 방법은 README에 기록된 명령을 기준으로 한다.
- 개인 PC에서만 동작하는 절대 경로를 코드에 작성하지 않는다.
- 운영체제별 경로 차이가 발생할 수 있으므로 `pathlib` 등 표준 경로 처리 방식을 우선 사용한다.

## 데이터 계약

클라이언트와 AI 모듈은 합의된 JSON 데이터 형식을 사용한다.

- 공통 필드 이름과 자료형을 임의로 변경하지 않는다.
- 필드를 추가하거나 삭제할 때는 클라이언트 팀과 먼저 협의한다.
- 필드가 없을 수 있는 경우 기본값 또는 `null` 처리 방법을 명시한다.
- `urgency_score`와 `relevance_score`는 `FilterResult` 데이터 계약에 따라 `1` 이상 `5` 이하의 정수로 표현한다.
- 모델 신뢰도를 별도로 사용할 경우 `model_confidence`는 `0.0` 이상 `1.0` 이하의 실수로 표현한다.
- `urgency_score`, `relevance_score`, `model_confidence`는 서로 다른 의미로 관리한다.
- 모델 신뢰도와 알림 중요도를 같은 의미로 사용하지 않는다.
- 날짜와 시간은 팀에서 합의한 형식으로 통일한다.
- 입력 순서에 따라 결과가 달라지는 기능은 알림의 기준 시각과 정렬 기준을 명확하게 한다.
- 다른 모듈이 기존 결과를 계속 사용할 수 있도록 가능한 한 하위 호환성을 유지한다.

공통 데이터 형태를 변경하는 PR에는 변경 전후의 JSON 예시를 함께 작성한다.

## 모델과 프롬프트

- 사용한 모델의 이름과 버전을 코드 또는 문서에 명시한다.
- 모델 입력과 출력 형식은 가능한 한 구조화된 JSON으로 정의한다.
- 프롬프트를 변경하여 출력 형식이나 판단 기준이 달라질 경우 관련 테스트와 예시도 함께 수정한다.
- LLM이 반환한 JSON은 그대로 신뢰하지 않고 파싱 실패, 필드 누락, 잘못된 자료형을 검사한다.
- LLM 호출 실패 시 사용할 기본값이나 대체 처리 방법을 마련한다.
- 중요도와 연관도는 서로 다른 개념으로 관리한다.
- 모델 성능에 영향을 주는 임계값과 가중치는 코드에 흩어놓지 않고 설정 파일 또는 상수로 관리한다.
- 학습이나 평가 결과를 공유할 때 사용한 데이터, 모델, 주요 설정과 평가 기준을 함께 기록한다.
- 재현 가능한 학습이 필요한 경우 난수 시드를 고정하고 사용한 설정을 저장한다.

## 데이터와 개인정보

- 실제 사용자의 알림, 대화 내용, 이름, 전화번호, 이메일 등 개인정보를 GitHub에 올리지 않는다.
- 개발과 테스트에는 가상 데이터 또는 익명화된 데이터를 사용한다.
- 개인정보가 포함될 수 있는 로그를 그대로 저장하거나 출력하지 않는다.
- 데이터 출처와 사용 가능 범위를 확인하고, 허가되지 않은 데이터를 학습에 사용하지 않는다.
- 가상 알림 데이터에도 실제 인물의 개인정보를 사용하지 않는다.
- 실제 알림을 외부 LLM API에 전달하기 전 이름, 전화번호, 이메일, 인증정보 등 개인정보를 마스킹한다.
- 외부 LLM API 호출 여부와 전송할 데이터 범위는 사용자 설정 및 팀의 개인정보 처리 방침을 따른다.
- API 요청 및 응답 전문을 로그나 GitHub에 저장하지 않는다.

다음 항목은 Git에 커밋하지 않는다.

- `.env` 및 API 키
- `.venv` 가상환경
- Python 캐시 파일
- 로컬 실행 로그
- 생성된 출력 파일
- 대용량 학습 데이터
- 대용량 모델 가중치 및 모델 캐시
- 실제 알림 및 개인정보가 포함된 파일

대용량 데이터나 모델 파일을 공유해야 하는 경우 팀원과 저장 위치와 공유 방식을 먼저 협의한다.

## 검증

변경한 기능은 PR을 만들기 전에 로컬에서 확인한다.

최소 확인 항목은 다음과 같다.

- 프로그램이 정상적으로 실행되는지 확인
- 가상 알림 JSON을 정상적으로 읽는지 확인
- 필수 출력 필드가 생성되는지 확인
- 잘못된 입력이나 빈 입력에서 프로그램이 중단되지 않는지 확인
- `urgency_score`와 `relevance_score`가 `1` 이상 `5` 이하의 정수인지 확인
- `model_confidence`를 사용하는 경우 `0.0` 이상 `1.0` 이하인지 확인
- 동일한 입력에 대해 예상한 그룹과 요약이 생성되는지 확인
- 일정이 없는 알림을 일정으로 잘못 생성하지 않는지 확인
- 외부 LLM 또는 API 호출 실패를 처리하는지 확인
- 클러스터별 요약이 원본 알림에 없는 내용을 생성하지 않는지 확인
- 일정 변경 및 취소 메시지에서 가장 최신 상태가 반영되는지 확인
- To-Do와 일정 후보가 원본 알림의 근거를 유지하는지 확인
- 스마트 답장 초안이 자동 전송되지 않고 사용자 확인 대상으로 반환되는지 확인
- TIL이 창 추적 로그와 알림 내용을 기반으로 생성되는지 확인

확인하지 못한 내용이나 알려진 문제는 PR 본문에 적는다.

## AI CI

CI는 `.github/workflows/ai-ci.yml` 하나로 구성할 예정이다. 기본 AI 모듈 구조와 README의 설치·실행·테스트 명령이 확정된 뒤 작성한다.

실행 조건은 다음과 같다.

- `develop`에 push
- `develop` 또는 `main` 대상 PR 생성 및 갱신

검사 순서는 다음과 같이 구성한다.

```text
Python 실행 환경 준비
→ 의존성 설치
→ 정적 검사
→ 단위 테스트
→ 가상 알림 데이터를 사용한 통합 테스트
```

CI에서는 실제 개인정보나 실제 Windows 알림을 사용하지 않는다. 테스트용 가상 알림 데이터를 사용한다.

외부 LLM API와 로컬 대규모 모델은 CI에서 직접 호출하지 않는 것을 원칙으로 한다. 모델 호출은 Mock 또는 고정된 예시 응답으로 대체하여 입출력 처리와 오류 대응을 검증한다.

실제 모델의 요약 품질, 분류 성능, 처리 속도는 별도의 고정 평가 데이터로 확인하며 일반 단위 테스트와 구분한다.

CI는 코드 실행과 데이터 계약 준수를 확인하지만, 실제 모델의 모든 품질과 사용자 환경에서의 성능을 보장하지 않는다.

`develop` 직접 push의 CI는 반영 후 실행된다. 실패하면 로그를 확인해 수정한다.
